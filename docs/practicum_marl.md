# Практическая работа: исследование стратегий мультиагентного управления в FlySwarm Student

## 1. Тема, цель и результат

**Тема:** сравнение программируемого агента, случайной стратегии и двух обучаемых политик PPO в среде мультиагентного управления.

**Цель:** самостоятельно разработать алгоритм поведения команды, изменить функцию вознаграждения, выполнить воспроизводимые эксперименты и аргументированно сравнить результаты.

По окончании работы студент должен представить два файла Python (агент и функция награды), результаты запусков, сравнительную таблицу, графики, пример визуального повтора и отчёт с выводами. **Победа PPO над Random не является обязательным результатом:** оценивается постановка и корректность эксперимента.

**Среда выполнения:** готовое приложение FlySwarm Student, раздел **MARL Laboratory**. Используйте студенческий релиз для своей ОС. Python, Godot, MaleCNS, исходники проекта и дополнительные зависимости для выполнения задания отдельно устанавливать не требуется. Достаточно встроенного редактора Python и команд лаборатории.

## 2. Как устроен эксперимент

В лаборатории моделируется бой 8×8: восемь машин студента против восьми машин контрольной команды. Все стратегии испытываются в одном аналитическом окружении на базе PettingZoo Parallel API. Состояния, награды, повреждения и победитель рассчитываются **Python-бэкендом**. Godot Viewer воспроизводит записанный результат; физику обычного игрового режима он для этих опытов не пересчитывает.

Возможны четыре исследуемые стратегии:

| Обозначение | Стратегия | Способ получения |
| --- | --- | --- |
| R | Random | Случайные управляющие действия |
| A | Student Agent | Собственный файл agent.py |
| P | PPO Standard | Обучение PPO со стандартной наградой |
| C | PPO Custom | Обучение PPO с собственной reward.py |

PPO обучает внешнюю управляющую политику. **Весовые файлы MaleCNS (brain.npz, weights.npz) здесь не изменяются; PPO не обучает сам коннектом.**

Стандартное наблюдение машины — массив из 30 чисел. Для управления используются шесть действительных значений от -1 до 1 в порядке: тяга, тормоз, поворот корпуса, поворот башни, угол возвышения орудия, выстрел. Контракт и индексы признаков приведены в [Python API MARL](marl_python_api.md) и во встроенной справке.

## 3. Вариант индивидуальной работы

**Каждый студент выполняет общие этапы 4–9, но выбирает один исследовательский вариант из таблицы.** Вариант определяет поведение собственного агента и главный акцент в собственной награде. Можно предложить оригинальный вариант преподавателю.

| Вариант | Поведение собственного агента | Проверяемая гипотеза |
| --- | --- | --- |
| 1. Захват точек | Движение к назначенной точке и удержание направления | Поощрение захвата повышает среднее число захватов |
| 2. Сохранение техники | Осторожное движение и ограничение риска | Увеличение штрафа за потерю машины сокращает средние потери |
| 3. Огневое воздействие | Выбор момента стрельбы и ориентирование на видимого противника | Поощрение урона повышает результативность стрельбы |
| 4. Командная координация | Использование act_team() для совместных решений | Координация восьми машин меняет распределение командных результатов |

Все варианты реализуются на **доступных агенту наблюдениях**, без скрытых координат и внутренних объектов симулятора. Для вариантов 1–3 допустимы act() или act_team(); для варианта 4 используйте act_team(). Студент самостоятельно выбирает правила, приоритеты, пороги и коэффициенты награды, объясняя их в отчёте.

**Не входят в задание:** смена состава машин, отключение ролевых признаков, перенастройка внутренних уровней A/B/C, установка новых алгоритмов через исходники, обучение MaleCNS. Эти возможности не нужны для сдачи практической через готовое приложение.

## 4. Подготовка и исходный эксперимент Random

1. Запустите FlySwarm Student → MARL Laboratory → «Эксперименты».
2. Запишите в отчёт версию приложения и платформу.
3. Выберите исходный seed, например **101**, и ограничение эпизода, например **150** шагов. Эти значения используйте в остальных основных запусках.
4. Нажмите «Запустить случайную политику». Через GUI выполняются **три эпизода**.
5. Откройте каталог результатов и найдите baseline.csv, evaluation.csv, summary.json, config.json и manifest.json, а также файлы повтора.
6. Запишите среднюю награду, победы/ничьи/поражения, захваты, уничтожения и потери. Для определения метрик опирайтесь на поля сохранённых данных.

**Random — исходный ориентир, а не итоговая независимая оценка.** Итоговые четыре стратегии сравниваются позднее одной командой на общих тестовых seed.

## 5. Создание собственной стратегии (agent.py)

1. Откройте вкладку «Python», выберите agent.py.
2. Измените предложенный шаблон: реализуйте **собственное нетривиальное решение** согласно варианту. Неизменённый стартовый код не считается завершённым алгоритмом.
3. Можно использовать NumPy, стандартную библиотеку Python и доступные по API поля observation/context. Не используйте скрытое состояние противника.
4. Функция act(observation, context=None) должна возвращать **ровно шесть конечных чисел** в диапазоне [-1, 1]. Альтернатива — act_team(observations, contexts), возвращающая по одному действию на каждого управляемого агента. При наличии act_team() именно она получает приоритет.
5. Если ваш алгоритм имеет внутреннее состояние, добавьте reset(seed), очищающий его перед эпизодом.
6. Сохраните код → «Проверить код» → «Запустить агента». В интерфейсе запускаются **три эпизода**.
7. Проанализируйте, действительно ли ваша стратегия движется, ориентируется, стреляет или согласует действия так, как предполагалось. Сохраните результаты и пример повтора.

Запуск пользовательского Python выполняется с правами текущего пользователя: **не загружайте и не запускайте недоверенные программы**.

## 6. Собственная награда (reward.py)

Создайте в соседнем редакторе reward.py. Главная функция — calculate_reward(components), либо расширенный вариант с публичными observation, action, next_observation и context.

Используйте только документированные компоненты (их знаки и единицы указаны в [Python API MARL](marl_python_api.md)):

- objective_progress, objective_approach, objective_capture;
- damage_dealt, enemy_kill, own_death;
- battle_win, battle_loss, battle_draw;
- ticket_delta, role_shaping и другие поддерживаемые в API.

**Задание:** сохраните разумный базовый смысл награды, измените коэффициенты в соответствии со своим вариантом и поясните ожидаемый эффект. Не обязательно добиваться лучшего результата: изменение награды — проверяемая гипотеза.

Проверьте код кнопкой «Проверить код». Функция обязана возвращать конечное число. Собственная награда влияет на **обучение PPO Custom**, но **не заменяет единую стандартную метрику** итогового сравнения.

## 7. Два обучения PPO

Все основные параметры эксперимента зафиксируйте в отчёте: seed, лимит эпизода, число переходов PPO и архитектуру.

**Рекомендуемый основной протокол:** одна и та же архитектура **«Общая политика на каждый танк» (parameter-sharing)**, один seed и одинаковое число переходов для P и C. Начните с короткой проверки, затем задайте примерно **8 192–16 384 перехода PPO** на каждое обучение, если позволяет компьютер. Если ограничены ресурсами, используйте меньше, но укажите число переходов и число реально завершённых эпизодов. Для этой архитектуры восемь переходов PPO соответствуют одному синхронному шагу мира.

1. В «Экспериментах» запустите «Обучить PPO и сохранить checkpoint» (P).
2. Дождитесь сохранения checkpoint и метрик; найдите файлы training.csv, ppo_metrics.csv, summary.json и изображения в plots/.
3. Не меняя параметры среды и архитектуру, запустите «Обучить PPO с reward.py» (C).
4. Убедитесь, что обе контрольные точки сохранены отдельно, а собственный reward.py записан вместе с результатом обучения.
5. При необходимости проверьте «Пауза / продолжить», «Остановить и сохранить» и «Продолжить выбранный checkpoint», но **не смешивайте неполные и законченные опыты в итоговом сравнении**.

Для первых коротких запусков график обучения может содержать мало точек или не иметь завершённых эпизодов. В таком случае увеличьте число переходов либо скорректируйте лимит эпизода и повторите **оба** обучения с одинаковыми новыми параметрами.

**Диагностика PPO:** ppo_diagnostics.png показывает policy gradient loss, value loss, entropy loss, approximate KL, clip fraction и explained variance. Ступени означают, что оптимизатор обновляет метрики периодически. Эти графики помогают изучать процесс оптимизации, но **не доказывают**, что политика научилась выигрывать. Основной вывод делайте по независимой оценке.

**Важно о шкалах:** у parameter-sharing PPO сохранённая учебная кривая может отражать среднюю награду отдельного агента, а не сумму наград всей команды. Не приравнивайте её по величине к командным наградам других архитектур. Для сравнения четырёх стратегий используйте **standard_evaluation_reward** в итоговых данных.

## 8. Независимая оценка и сравнение

1. Выберите сохранённый checkpoint и выполните «Оценить модель на тестовых seed».
2. Выполните «Сравнить Random и PPO на одинаковых seed». Это дополнительная проверка различий двух стратегий.
3. После сохранения **обоих** checkpoint и рабочего agent.py нажмите «Сравнить четыре стратегии на одинаковых условиях».
4. Убедитесь, что сравниваются R, A, P и C. Через GUI используются **три тестовых seed**, отличных от обучения, и две конфигурации стартовых сторон. Изучайте эти две конфигурации раздельно; не считайте зеркальные старты шестью независимыми seed.
5. Откройте comparison.csv и summary.json. Для итогового отчёта приведите одинаково рассчитанные метрики по каждой политике.

При исходном seed 101 окно четырёхстороннего сравнения использует тестовые seed 2101–2103. Для повышения надёжности можно повторить сравнение с иным базовым seed (например, 5001 → тестовые 7001–7003), не переобучая модели. Опишите оба запуска отдельно.

Таблица для отчёта:

| Стратегия | Средняя стандартная награда | Победы (%) | Захваты (среднее) | Уничтожения (среднее) | Потери (среднее) |
| --- | --- | --- | --- | --- | --- |
| R — Random | | | | | |
| A — Agent | | | | | |
| P — PPO Standard | | | | | |
| C — PPO Custom | | | | | |

Если метрики противоречат гипотезе, это полноценный исследовательский результат. Сравнение тренировочных наград со значениями независимой оценки **недопустимо**.

## 9. Визуальный повтор и экспорт

1. Откройте один повтор Random, один повтор собственного агента и один повтор PPO через кнопки лаборатории или «Открыть любой повтор…».
2. Опишите минимум два наблюдаемых различия поведения. Сопоставьте увиденное с CSV/JSON; не делайте количественный вывод по одному красивому бою.
3. Во вкладке Python откройте меню «⋯» → «Экспортировать практическую…».
4. Проверьте ZIP: он должен содержать ваши agent.py и reward.py, manifest, конфигурации, численные результаты, графики, checkpoint и файлы повторов **для действительно созданных запусков**. Наличие каждого вида файла зависит от типа завершённого эксперимента.

## 10. Отчёт и сдача

Объём: ориентировочно **4–7 страниц** без приложений. Структура:

1. Тема, вариант, цель и проверяемая гипотеза.
2. Выбранная стратегия (описание алгоритма и использованных входных признаков).
3. Собственная функция награды: формула/веса и обоснование.
4. Параметры опыта: версия приложения, платформа, seed, лимит эпизода, архитектура PPO, число переходов и количество завершённых эпизодов.
5. Четырёхстороннее сравнение, таблица стандартных метрик, график обучения или диагностики с пояснением.
6. Краткий анализ replay и ограничения аналитической модели.
7. Вывод: подтвердилась ли гипотеза, насколько надёжен результат и что следует изменить в следующем опыте.

**Сдать:** отчёт в PDF и экспорт ZIP из лаборатории. При необходимости приложить один-два скриншота, подтверждающие запуск/сравнение.

На защите объясните, чем индивидуальная act() отличается от act_team(), чем training reward отличается от standard evaluation, почему нужны независимые seed, что означает параметр PPO transitions и почему эти испытания не являются физической проверкой брони и баллистики Godot.


## 11. Ограничения и безопасность

Лаборатория использует аналитический мир 8×8, а не физический боевой движок OpenDay. В аналитическом опыте нейронные признаки MaleCNS могут быть нулевыми; текущая практическая не исследует причинный вклад коннектома. Студенческий Python выполняется в отдельном процессе с тайм-аутами, но без полноценной системной песочницы.

Число тестовых эпизодов в GUI сейчас фиксировано; масштабируйте объём доказательств повторными независимыми сравнениями, а не несуществующими пунктами настроек. Варианты, отсутствующие в интерфейсе, **не являются обязательными**. При неисправности функции приложения сообщите преподавателю, приложив версию и журнал ошибки.
